# B0.1 — Buyer, seller, driver, and operator journeys

Owner: Person B
Wave: 0 (team foundation)
Depends on: none
Blocks: none
Status: documentation-only, no application code touched

## Goal

Document the core end-to-end journeys for all four marketplace roles, each
with an initial low-fidelity wireframe and acceptance criteria, so that
downstream Wave 1–3 issues (B1.1 catalog, B2.1 checkout, B3.1 buyer
lifecycle, C1.1 driver availability, C2.3 driver screens, C3.2 ops
dashboards, etc.) have an agreed shape to implement against instead of
inventing UX on the fly.

## Context

Per `TEAM_PIPELINE.md` §2, Person B owns the buyer cart/checkout
experience, seller dashboard, and order-management experience. This issue
is the Wave 0 documentation groundwork for that ownership. It intentionally
produces no code — it produces a shared reference other issues can point
back to.

The first release is a single-driver-per-delivery marketplace
(`TEAM_PIPELINE.md` §1); the driver journey below is scoped to that
constraint. Multi-driver handoff is out of scope until Wave 4.

## Wireframe format

Wireframes for this issue are low-fidelity step-flow sketches (box/arrow
diagrams), not high-fidelity screen mockups. They were reviewed live with
the author as inline diagrams; this file captures the same structure in
text so it survives outside that chat session. Higher-fidelity screen
mockups belong to the individual Wave 1–3 issues (e.g. B1.1, B2.1) once
each screen is actually being built.

## 1. Buyer journey

1. **Browse catalog** — search and filter products.
2. **View product detail** — photos, price, seller info.
3. **Add to cart and checkout** — address, server-validated quote, payment
   method.
4. **Track order** — status updates, delivery ETA.
5. **Receive and review** — confirm delivery, rate seller.

### Acceptance criteria

- [ ] A buyer can move from catalog browse to a placed order without a
      dead end or unexplained state.
- [ ] Checkout is documented as producing a server-validated quote, not a
      client-computed price (this is the contract `B2.1` will implement
      once `A2.1` merges).
- [ ] Order tracking and the post-delivery review step are both present in
      the journey (feeds `B3.1`).

---

## 2. Seller journey

1. **Onboard and list products** — add photos, price, stock.
2. **Manage inventory** — update stock, edit listings.
3. **Receive order** — new order notification.
4. **Accept and pack** — confirm items, prepare handoff to driver.
5. **View sales and payout** — track earnings, fees, refunds.

### Acceptance criteria

- [ ] A seller can go from zero listings to a packed, handed-off order
      using only steps in this journey.
- [ ] The journey shows the seller only ever acting on their own listings
      and orders (ownership scoping enforced later in `B1.2`/`B2.2`).
- [ ] Payout/fee visibility is deferred to `B3.2` and depends on `A3.2` —
      noted here so it isn't silently promised earlier.

---

## 3. Driver journey

1. **Go online** — set availability status.
2. **Accept assignment** — review pickup and drop details.
3. **Confirm pickup** — verify items with seller.
4. **In transit** — navigate to buyer address.
5. **Deliver and confirm** — OTP confirmation, then go offline or take the
   next assignment.

### Acceptance criteria

- [ ] The journey is single-driver-per-delivery only, consistent with
      `TEAM_PIPELINE.md` §1 — no handoff-to-another-driver step.
- [ ] OTP-based delivery confirmation is shown as the terminal success
      state (matches `C2.3`'s exit condition).
- [ ] A failure/exception path (failed delivery, no OTP match) is called
      out as a known gap for `C2.3` to design in detail — not solved here.

---

## 4. Operator journey

1. **Monitor dashboard** — orders, deliveries, exceptions.
2. **Detect exception** — failed assignment, delay, dispute.
3. **Intervene** — reassign driver, contact parties.
4. **Resolve support ticket** — handle buyer or seller issue.
5. **Review reports** — SLAs, driver performance.

### Acceptance criteria

- [ ] The journey covers both reactive (exception handling) and periodic
      (reporting) operator work.
- [ ] Ownership of operator tooling is flagged as an open question below
      rather than assumed.
